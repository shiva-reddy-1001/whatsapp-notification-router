# Message Notification Router — Low-Level Design

> **v2 supersession (August 2026):** The original in-memory design is retained
> below as the baseline. The active implementation now uses a local SQLite
> cache for media extraction and ambiguous provider decisions, an explicit
> feature-extraction layer, and a versioned case-file prompt (`router-casefile-v2`).
> SQLite is the authoritative local execution store; an external vector DB is
> intentionally deferred because the dataset is small and reproducibility is
> more valuable than infrastructure.

## v2 feature-pipeline contract

```text
CSV sources → normalized case → cached OCR/ASR → auditable features
  → two-stage historical retrieval → deterministic safety gate
  → cached structured-model decision for ambiguous cases → output validator
```

The feature extractor outputs only facts (`risk`, `priority`, and
`noise/fatigue`). Routing policy consumes those facts separately. This replaces
the earlier mixed rule-and-feature implementation and makes threshold tuning
and error analysis safe.

Cache keys include source identity/configuration (media file modification time,
provider/model, prompt version, and full case file). This provides safe resume
behavior without reusing a response after its inputs or policy change. Cache
files live under ignored `.router-cache/` and must never contain credentials.

The v2 master prompt has hard policy precedence, injection resistance, an
allowed-label contract, compact source facts, media quality, and only
retrieval-approved evidence IDs. It is not a replacement for safety rules;
clear safety outcomes bypass model calls.

## 1. Goal and non-negotiable contract

For every row in `dataset/messages.csv`, produce exactly one row in
`dataset/output.csv` with these columns, in this exact order:

```text
message_id,action,message_type,reason,confidence,evidence_message_ids
```

Allowed actions are `notify`, `digest`, and `mute`. Allowed message types are
`personal`, `urgent`, `event`, `payment`, `business_update`, `promotion`,
`greeting`, `forward`, `spam`, `scam`, and `unknown`.

The router is personalized: the same message can legitimately result in a
different action for different recipients. It must be deterministic where
practical, runnable from the terminal, and use only participant-facing files
inside `dataset/`.

## 2. Design principles

1. **Safety overrides preference.** Clear scams, suspicious credential/OTP
   requests, and high-risk payment requests are muted before personalization.
2. **Interruptions need a higher bar.** `notify` requires urgency or strong
   personal relevance; ordinary usefulness belongs in `digest`.
3. **History must be attributable.** Only retrieve historical messages that
   genuinely support the decision, and cite their IDs in the output.
4. **Structured features constrain the model.** The LLM (if used) judges a
   compact case file rather than raw CSV data; rules validate its decision.
5. **Media is content.** Image OCR/understanding and voice transcription are
   treated as message text, with explicit uncertainty metadata.
6. **Output is a product surface.** The output writer validates schema,
   allowed values, uniqueness, row count, confidence bounds, and evidence IDs.

## 3. Provider-neutral runtime configuration

The router must run without code edits in three modes:

1. **OpenAI API mode** when a judge or user supplies `OPENAI_API_KEY`.
2. **Local Ollama mode** for development without a cloud credential.
3. **Rules-only mode** when no model provider is available, so validation and
   the deterministic baseline remain runnable everywhere.

`OPENAI_API_KEY` is the canonical OpenAI environment variable. Do not use the
misspelling `OPENAI_API_KY`, custom aliases, hardcoded keys, or a committed
`.env` file. The official SDK reads `OPENAI_API_KEY` from the environment by
default, so a judge runner can replace the key and invoke the same command
without any code or configuration change. [OpenAI quickstart](https://platform.openai.com/docs/quickstart/make-your-first-api-request)

### 3.1 Configuration precedence

```text
explicit CLI flags
  > environment variables
  > checked-in non-secret config defaults
  > safe built-in defaults
```

Use a checked-in `config/defaults.yaml` (or equivalent dataclass) for model
names, thresholds, timeouts, and prompt versions. Use `.env` only for local
development, exclude it with `.gitignore`, and never require it in production
or the judge runner.

### 3.2 Environment contract

| Variable | Values / default | Meaning |
|---|---|---|
| `ROUTER_LLM_PROVIDER` | `auto` (default), `openai`, `ollama`, `rules` | Provider selection. |
| `OPENAI_API_KEY` | unset by default | OpenAI API credential; never log or print it. |
| `OPENAI_MODEL` | configured default | OpenAI model identifier, used only in OpenAI mode. |
| `OLLAMA_BASE_URL` | `http://127.0.0.1:11434` | Local Ollama server URL. |
| `OLLAMA_MODEL` | configured default | Installed Ollama generation model name. |
| `ROUTER_EMBEDDING_PROVIDER` | `none` / `openai` / `ollama` / `local` | Optional semantic retrieval backend. |
| `ROUTER_REQUEST_TIMEOUT_S` | configured finite value | Per-request timeout. |
| `ROUTER_MAX_RETRIES` | configured finite value | Retry count for transient provider failures. |
| `ROUTER_CACHE_DIR` | project-local cache path | Media/model cache location; no secrets. |
| `ROUTER_AUDIO_TRANSCRIBER` | `faster_whisper` | Local voice-note transcription adapter. |
| `ROUTER_WHISPER_MODEL` | `tiny` | Cached Whisper model; deliberately small for local development. |
| `ROUTER_WHISPER_COMPUTE_TYPE` | `int8` | Low-memory local Whisper inference setting. |

CLI flags mirror these names (for example, `--provider`, `--model`, and
`--ollama-base-url`) but never accept a raw API key. Credentials must come
from the process environment or a local ignored `.env` loader.

### 3.3 Provider resolution

```text
if ROUTER_LLM_PROVIDER is openai:
    require OPENAI_API_KEY; otherwise fail with setup guidance
elif ROUTER_LLM_PROVIDER is ollama:
    require a reachable OLLAMA_BASE_URL and named OLLAMA_MODEL
elif ROUTER_LLM_PROVIDER is rules:
    use deterministic classifier only
elif ROUTER_LLM_PROVIDER is auto:
    use OpenAI if OPENAI_API_KEY is set
    else use Ollama if its health check and configured/default model succeed
    else use rules-only mode
```

`auto` makes the standard judge invocation seamless: when the runner injects
`OPENAI_API_KEY`, the exact normal command selects OpenAI. Local development
can force `ollama` to avoid accidental cloud usage. The resolved provider,
model, and non-secret endpoint are written to run metadata, never to
`output.csv` and never with credentials.

### 3.4 Common provider interface

Keep all call sites independent of SDK/vendor details:

```python
class StructuredClassifier(Protocol):
    def classify(self, case_file: CaseFile) -> ClassifierResult: ...

class MediaTranscriber(Protocol):
    def transcribe(self, path: Path) -> Transcript: ...

class Embedder(Protocol):
    def embed(self, texts: list[str]) -> list[list[float]]: ...
```

Implement `OpenAIClassifier`, `OllamaClassifier`, and `RulesClassifier` behind
`StructuredClassifier`. All must consume the same prompt contract and return
the same validated `ClassifierResult`. Keep OCR and transcription adapters
separate, so a provider change affects only the relevant capability.

### 3.5 Capability and fallback policy

| Capability | OpenAI mode | Ollama mode | Rules mode |
|---|---|---|---|
| Structured final classification | API adapter | local adapter | deterministic fallback |
| Image understanding | configured API model or OCR | optional local vision model plus OCR | OCR/metadata only |
| Voice transcription | configured API/local adapter | optional local adapter | no transcript; lower confidence |
| Semantic retrieval | optional configured embedder | optional local embedder | lexical retrieval |

The pipeline must not silently substitute a model with incompatible output.
Each adapter advertises capabilities, validates structured output, and reports
an actionable non-secret setup error when explicitly requested capability is
missing. In `auto`, an unavailable optional capability degrades to the
documented deterministic alternative and lowers confidence.

### 3.6 Operational commands

The final README should document one invariant command plus explicit local
alternatives:

```bash
# Judge/OpenAI: judge injects OPENAI_API_KEY, no source change required.
python code/main.py --input dataset/messages.csv --output dataset/output.csv

# Local Ollama development.
ROUTER_LLM_PROVIDER=ollama OLLAMA_MODEL=<installed-model> \
  python code/main.py --input dataset/messages.csv --output dataset/output.csv

# Deterministic debugging and CI without any model service.
ROUTER_LLM_PROVIDER=rules \
  python code/main.py --input dataset/messages.csv --output dataset/output.csv
```

Do not make model installation part of normal judge execution. Document it as
an optional local setup step, pin model names in non-secret config, and add a
`--check-config` command that validates provider resolution before processing
the full dataset.

### 3.7 Provider test matrix

Run the same sample-set and output-contract suite in these configurations:

| Scenario | Required result |
|---|---|
| `rules` | Valid deterministic output, no network/model dependency |
| `ollama` | Successful local health check and schema-valid results |
| `openai` with injected `OPENAI_API_KEY` | Successful API call; key absent from logs/output |
| `auto` with API key | Resolves to OpenAI |
| `auto` without key, reachable Ollama | Resolves to Ollama |
| `auto` without either service | Resolves to rules-only with valid output |

## 5. Data model and indexes

### 4.1 Primary input record

Normalize each incoming row to an `IncomingMessage`:

```text
message_id, user_id, conversation_type, group_id, business_id,
sender_user_id, created_at, message_text, media_type, media_id,
forwarded_count
```

Empty CSV values become `None`, timestamps become timezone-aware datetimes
(dataset-local time unless metadata specifies otherwise), and numeric fields
become numbers.

### 4.2 Lookup indexes built once

| Source | Index | Purpose |
|---|---|---|
| `users.csv` | `user_id` | DND window and baseline engagement/risk signals |
| `groups.csv` | `group_id` | Group type, size, and activity |
| `group_members.csv` | `(group_id, user_id)` | Role, mute state, user engagement in group |
| `business_accounts.csv` | `business_id` | Verification, brand/domain consistency, reports |
| `user_business_history.csv` | `(user_id, business_id)` | Relationship, activity, consent, prior engagement |
| `message_history.csv` | user/sender/group/business keys | Historical retrieval candidates |
| `message_events.csv` | `message_id` plus user | Open/reply/dismiss/mute/report outcomes |
| `images.csv`, `voice_notes.csv` | media ID | Local media file resolution |
| `daily_notification_summary.csv` | `(user_id, date)` | Notification burden / fatigue |

### 4.3 Historical enrichment

Join every historical message with its interaction event. Derive labels such
as `engaged` (opened/replied), `ignored` (dismissed), `reported`, and
`muted_after`. Historical data is evidence, not ground-truth labels for the
incoming rows.

## 6. Per-message case-file builder

The classifier consumes one compact `CaseFile` per message. This prevents a
large prompt from hiding important facts.

```text
CaseFile
  message: IDs, timestamp, conversation type, original text, forwarded count
  normalized_content: text + media extraction + extraction confidence
  recipient: DND status, engagement baseline, report/dismissal tendencies,
             recent notification load
  conversation: group metadata/member relationship OR business metadata/user
                relationship OR personal sender context
  risk_signals: domain mismatch, credential request, scam cues, reports, etc.
  priority_signals: deadline, direct mention, explicit request, urgency,
                    trusted sender/admin, user relationship
  noise_signals: campaign repetition, promotion opt-out, forwarding, muted
                 group, historical dismissals
  retrieved_history: at most 3–5 compact examples with message ID, text
                      summary, interaction outcome, and relevance rationale
```

### 5.1 Derived recipient features

- `is_in_dnd`: message time falls within `do_not_disturb_window`.
- `notification_load`: same-day notifications and dismissal rate, relative to
  that user's recent baseline.
- `fatigue_level`: low/medium/high based on notification load and recent
  dismissals; it raises the bar for `notify`, but never suppresses real safety
  or emergency content.

### 5.2 Conversation features

**Group:** group type, member count, activity, whether recipient muted it,
recipient's role and group engagement, and whether the sender is an admin.

**Business:** verified status, official-domain match, account age, report rate,
relationship type, recent activity, promotion permission, and opt-out date.

**Personal:** sender identity if available, direct request/mention, prior
interaction history, and conversational urgency.

## 7. Multimodal processing

### 6.1 Images

1. Resolve `media_id` through `images.csv` and validate the local path.
2. Run OCR to extract visible text, URLs, prices, dates, deadlines, and
   payment/OTP language.
3. Optionally use image understanding for non-text context (poster, receipt,
   screenshot, product promotion, warning notice).
4. Store a cached result keyed by media ID:

```json
{"text":"...","description":"...","urls":["..."],"quality":0.0}
```

5. Concatenate the extraction with `message_text`, preserving its source.

### 6.2 Voice notes

1. Resolve `media_id` through `voice_notes.csv`.
2. Transcribe locally or through a configured transcription API.
3. Cache transcript, language, duration (if available), and transcription
   confidence by media ID.
4. Use transcript content in the same safety, retrieval, and classification
   path as text messages.

### 6.3 Graceful degradation

Missing/unreadable media does not fail the run. Set extraction quality to zero,
classify from available metadata/text, lower confidence, and retain a concise
reason without claiming unseen content.

## 8. Safety, urgency, and noise feature extraction

All feature functions return machine-readable flags plus human-readable facts
for the case file.

### 7.1 Safety signals

- OTP, PIN, password, credential, or remote-access request.
- Suspicious payment pressure, delivery fee, account-blocked, or reward claim.
- Domain mismatch: sender domain differs from the verified official domain.
- Lookalike/untrusted domain, recently created sender domain, elevated reports.
- Scam-like forwarded content, explicit report history, or repeated abuse.

**Override:** strong scam evidence produces `mute` / `scam`; clear bulk junk
produces `mute` / `spam`. The final classifier cannot overturn a high-severity
safety decision without an explicit, audited exception.

### 7.2 Priority signals

- Same-day or near-term deadline, emergency, service interruption, or payment
  required to prevent a concrete consequence.
- Trusted group admin delivering a recipient-relevant operational update.
- Direct mention, direct question, or explicit action required from recipient.
- Active business relationship: expected delivery, booking, payment, or order.

### 7.3 Noise signals

- User opted out of promotions or repeatedly dismissed this business/category.
- Recipient muted the group and the message lacks direct urgency/mention.
- Near-duplicate history/campaign messages.
- High forwarding, generic greetings, vague invitations, or low-relevance ads.

## 9. Historical retrieval and evidence selection

This is targeted retrieval, not a general-purpose vector database requirement.

### 8.1 Candidate generation

Start with a union of candidates for the same recipient:

1. same `(user_id, business_id)`;
2. same `(user_id, group_id)`;
3. same `(user_id, sender_user_id)`;
4. same conversation type or message-type cues;
5. lexical/semantic matches over normalized text and media extraction.

Restrict to historical messages that precede the incoming message timestamp.

### 8.2 Candidate scoring

Rank candidates by a weighted, deterministic score:

```text
0.35 content similarity
+ 0.25 same sender/group/business
+ 0.20 interaction outcome relevance
+ 0.10 recency
+ 0.10 matching risk or priority pattern
```

Use lexical similarity first; add embeddings only if available and cache them.
Avoid external retrieval infrastructure unless the dataset size proves it is
needed.

### 8.3 Evidence policy

- Return no more than three evidence IDs in chronological/relevance order.
- Cite only messages that materially support the final outcome.
- Prefer prior dismissals/opt-outs for `mute`, prior engagement/replies for
  `notify`/`digest`, and prior reports for safety outcomes.
- Use `none` when no candidate clears a relevance threshold.

## 10. Decision policy

Decision runs in this order:

```text
1. Validate and normalize message
2. Extract media content
3. Build features and retrieve history
4. Apply non-overridable safety rules
5. Apply deterministic high-certainty rules
6. Use structured classifier for ambiguous cases
7. Postprocess: enforce rules, select evidence, calibrate confidence
8. Validate and write output
```

### 9.1 High-certainty rules

| Condition | Action / type |
|---|---|
| Strong scam or credential/payment fraud indicators | `mute` / `scam` |
| Bulk junk or repeated unwanted campaign | `mute` / `spam` or `promotion` |
| Trusted, time-sensitive operational message or direct urgent request | `notify` / `urgent` or `event` |
| Legitimate active-order/payment/booking update without immediate deadline | `digest` / `business_update` or `payment` |
| Promotion from opted-out or repeatedly dismissed source | `mute` / `promotion` |

The prompt is used when signals conflict or the content requires nuanced
interpretation—not for obvious rule outcomes.

## 11. Structured classifier prompt

Do not use one unconstrained "God prompt." Use a versioned decision prompt
with a compact case file and a strict JSON response schema.

### 10.1 Prompt objectives

- Select only allowed action and message type values.
- Make an interruption-aware, personalized decision.
- Treat risk as higher priority than engagement.
- Cite only IDs supplied in `retrieved_history`.
- Explain in one short, factual sentence.
- Return calibrated confidence, not a probability invented without evidence.

### 10.2 Response schema

```json
{
  "action": "notify|digest|mute",
  "message_type": "personal|urgent|event|payment|business_update|promotion|greeting|forward|spam|scam|unknown",
  "reason": "Short factual explanation.",
  "confidence": 0.0,
  "evidence_message_ids": ["message_0001"]
}
```

Programmatic validation rejects invalid JSON/labels, strips unsupported
evidence IDs, clamps confidence to `[0, 1]`, and falls back to deterministic
rules if the model response cannot be repaired.

## 12. Confidence calibration

Start from rule/model confidence, then adjust based on the evidence quality.

| Evidence state | Typical confidence |
|---|---|
| Clear safety pattern or explicit trusted same-day urgency | 0.82–0.95 |
| Strong structured context plus relevant history | 0.72–0.88 |
| Clear content but sparse personal history | 0.60–0.76 |
| Ambiguous content, poor media extraction, or conflicting signals | 0.40–0.65 |

Confidence should decrease when OCR/ASR quality is low, no contextual record
exists, or high-value signals conflict. It should not be inflated because the
output format requires a number.

## 13. Reasons and output writer

Reasons should be concise, specific, and grounded in available information.
Good: "A trusted school admin sent a same-day bus schedule change." Bad:
"This message is important." Never reveal hidden chain-of-thought; give only
the user-facing decision rationale.

`output_writer.py` enforces:

- one unique output row for each input `message_id`;
- exact column order and no extra columns;
- allowed labels only;
- finite numeric confidence in `[0, 1]`;
- `none` or semicolon-separated IDs from `message_history.csv` only;
- UTF-8 CSV escaping and deterministic input order.

The current template should not control prediction count. Generate the output
from `messages.csv` and validate against its parsed rows. As of this dataset
revision it contains 110 target messages; multiline CSV text means physical
line counts are not reliable.

## 14. Evaluation strategy

`sample_messages.csv` contains solved examples and is the development oracle.
Never use its labels as hidden-test predictions; use it to test the pipeline.

For every iteration:

1. Run the pipeline on sample rows.
2. Compare action and message type accuracy.
3. Audit mismatches by action/type, conversation type, media type, and
   rule-vs-model route.
4. Manually inspect whether the reason is factual and evidence is relevant.
5. Tune thresholds, retrieval weights, or prompt wording; record changes.
6. Re-run deterministic validation and retain an evaluation report.

Prioritize reducing dangerous false `notify` decisions for suspicious content,
then improve recall for real time-sensitive group/personal updates.

## 15. Execution plan

### Phase 0 — Inventory and baseline

- Inspect all schemas, row counts, null patterns, date ranges, sample labels,
  media availability, and existing project code.
- Implement provider resolution, `--check-config`, non-secret defaults, and
  provider-independent rules-only execution before introducing SDK calls.
- Establish a baseline heuristic router and full output validator.
- Write setup/run instructions before adding optional model dependencies.

**Done when:** a terminal command generates one valid output row for every
parsed input message deterministically.

### Phase 1 — Data and context foundation

- Implement typed CSV loader and all lookup indexes.
- Build case files and derived DND, fatigue, group, business, and relationship
  features.
- Build historical-message/event enrichment and candidate indexes.

**Done when:** case-file debug output is correct for representative personal,
group, and business messages.

### Phase 2 — Deterministic routing and retrieval

- Implement safety, priority, and noise feature detectors.
- Add high-certainty action/type rules.
- Implement candidate generation, scoring, relevance threshold, and evidence
  selection.
- Evaluate the rule-only baseline on samples.

**Done when:** every baseline decision includes valid evidence semantics and
obvious scam/promotion/urgent cases follow the intended policy.

### Phase 3 — Multimodal pipeline

- Add image OCR plus optional image understanding.
- Add voice transcription.
- Cache all media results and handle absent/unreadable files safely.
- Re-run sample evaluation, segmented by media type.

**Done when:** media-derived text reaches the same case-file and classifier
path as native text.

### Phase 4 — Structured classifier integration

- Implement prompt construction and JSON-schema validation.
- Implement OpenAI and Ollama adapters behind the common provider interface;
  test explicit provider modes and `auto` resolution without changing code.
- Route only ambiguous messages to the model; cache by case-file hash.
- Add postprocessing/guardrails and calibrated confidence.
- Compare rule-only and hybrid outputs on the solved sample set.

**Done when:** invalid model responses cannot corrupt output and the hybrid
system demonstrably improves or clarifies sample decisions.

### Phase 5 — Quality gate and submission package

- Run a complete clean-room generation from the terminal.
- Validate all output invariants and inspect a stratified sample manually.
- Verify no organizer-only files, hardcoded labels, secrets, or broken paths.
- Package code, README, prompts/configuration, evaluation artifacts, final
  `output.csv`, and required chat transcript according to submission rules.

**Done when:** another machine/user can follow the README and reproduce a
valid `output.csv`.

## 16. Open decisions before implementation

1. Which local Ollama model(s) are practical for this machine's memory and
   sufficiently reliable at instruction following and JSON output? Install and
   test them locally only; judge mode must not assume Ollama is installed.
2. Which local/API OCR and transcription adapters are available under the
   challenge runtime and key constraints?
3. Should embeddings be added after lexical retrieval baseline results, or is
   deterministic keyword/sender retrieval sufficient for this data size?
4. What sample-set metrics and error categories will be recorded as the
   acceptance gate for each phase?
5. How much latency/cost is acceptable for 264 messages, especially for media
   processing and LLM calls?
